Architecture / Product Explanation

WhatsApp SaaS — Reliable Queue & Failure Recovery Architecture

A presentation-ready architecture for managing multiple clients, WhatsApp instances, prioritized message queues, controlled pacing, retries, account health, and safe pause/resume behavior.

Clients
100+

Each client can have an independent WhatsApp instance and queue.

Queued messages
10,000+

Messages remain durable while workers process them gradually.

Core principle
Fail Safe

When an account becomes unavailable, sending pauses instead of endlessly retrying.

Key idea: API requests should not directly perform thousands of sends. The API creates durable jobs; workers process those jobs under account-level controls.

2. Multi-Client / Multi-Account Isolation

      ├── Worker

Client C
  └── WA-C
      └── ...

Why isolate queues?

  • One client's campaign should not block another client's messages.
  • Account health is tracked independently.
  • Pause/resume can happen per WhatsApp instance.
  • Scaling workers becomes easier.

Suggested infrastructure: PostgreSQL for durable business/message state, Redis for fast queueing/locks/rate state, and stateless API/worker services.

3. Priority Queue

Priority controls which eligible job gets processed first. It should not be treated as a promise of a specific delivery speed.

HIGH
Preferred
NORMAL
Balanced
LOW
Background

Use weighted/fair scheduling so a continuous HIGH stream cannot starve NORMAL or LOW jobs forever.

5. Message Lifecycle

1
CREATED

Client submits a message/campaign. API validates it and creates a durable job.

2
QUEUED

Job waits in the account's queue with priority and scheduling metadata.

3
PROCESSING

Worker claims the job using a lock/idempotency mechanism.

4
SENT / FAILED

Provider response is stored. Successful jobs become SENT; retryable failures return to the queue.

5
FINAL

After successful delivery or a non-retryable failure, the job stops being retried.

7. Restriction / Account Failure Recovery

SendingCONNECTED
→
Failure signalERROR
→
Pause instancePAUSED
→
User notificationDashboard / webhook
WA-A
├── Sent:       600
├── Processing:   0
└── Queued:    1,399

WA-A → PAUSED
       ├── No new sends
       ├── Existing jobs preserved
       └── User notified

After legitimate recovery:
PAUSED → READY → QUEUED → PROCESSING → SENT
Do not design: automatic number rotation, fake identities, proxy tricks, or other mechanisms intended to evade a provider restriction. The safe design is to stop, preserve pending work, inform the user, and use the provider's legitimate recovery/appeal/reconnection path.

10. Redis / Queue Responsibilities

Queue

Store pending jobs and expose eligible jobs to workers.

Rate / pacing state

Keep short-lived per-instance scheduling and concurrency state.

Locks

Prevent two workers from processing the same job simultaneously.

14. Recommended Product Positioning

Reliable WhatsApp messaging infrastructure — controlled queues, priority scheduling, delivery tracking, account-level pacing, health monitoring, and safe pause/resume recovery.

This positioning is stronger than promising “instant bulk sending” or implying that a specific delay can prevent provider restrictions.
