# P24 — groups-messaging

**Goal (one line):** A tenant can sync the groups an account is already in, enable sending per group, send into a group under its own much smaller daily cap, see group delivery/read receipts that never collide with 1:1 receipts, run a group broadcast (`target_kind='groups'`), and have a group 403 disable **that group only** — never pause the number.
**Status:** done (2026-09-06) · **Size:** M · **Session:** 1 of 1
**Depends on:** P14, P21, P23 (must be `done`)
**Blocks:** P25

- `capture_groups` / `capture_media` are **v2 columns and do not exist in v1** (ADR 0021). Group message storage is v2; this phase sends to groups and records receipts only.
- ADRs **0013, 0015, 0017, 0018, 0019, 0020 accepted**.
- **O3:** no `/feature` run. The design is fully specified in the scope delta's *Groups* section and ADR 0017 §2. The only open judgement is the **UI wording of the device-budget refusal** (step 5) and it must follow the copy rules below.

## What you are building (3-6 bullets)
- `wa_groups` + an hourly-at-most sync that stores subject, `participant_count`, `is_announce`, `our_role`, `tracked_participant_devices` — and **never a participant list**.
- Per-group `send_enabled` opt-in, gated additionally by the per-instance 2,000 tracked-participant-device budget, plus the leave action; **no add/remove/promote/create path exists in the codebase at all**.
- The group send path: `is_group` through claim → reserve (one general unit **plus** one group unit), `is_new_conversation=false`, `recipient_hash = hmac(pepper, group_jid)`, excluded from the opt-out gate and the per-recipient frequency guard, still content-guarded and window-bound, charged once at `group_text`/`group_media`.
- The terminal `group_forbidden` class: an authorisation 403 on a `@g.us` target fails that one job, sets `send_enabled=false` for that group, triggers a re-sync — and **never** contributes to the hard-restriction signal.
- Group receipts: `participant_jid` in `provider_event_id`, `shouldIgnoreJid` narrowed so it can only drop group **message** events, and no group-message filter consulted anywhere in the receipt path.
- Group broadcasts via `campaigns.target_kind='groups'`, and the group panel carrying the required report-risk copy verbatim.

**Design decisions taken at open (recorded at C6):**
- **No participant list is cached anywhere, Redis included.** Baileys' `cachedGroupMetadata` is NOT supplied: it must return participant lists, and ADR 0017 §2 plus this phase's risk list forbid storing one "in any form". This deviates from step 4's *mechanism* ("from redis-cache") to honour its *rule* ("counts only... no participant JIDs reach Redis").
- `subject_owner_jid_hash` (delta DDL) is omitted from `wa_groups`: a participant-derived identity with no v1 consumer.
- One per-instance sync clock on `whatsapp_instances`: `groups_next_sync_after`, `groups_sync_requested_at`, `groups_last_synced_at`. The worker syncs an owned instance only when the clock allows AND (a tenant requested it, or it has a `send_enabled` group, or a group carries `next_sync_after <= now()` from a `group_forbidden`) - so a number whose tenant never uses groups generates zero provider calls, and a 403 storm can never become a fetch storm. Sync and leave execute in the **session worker** (the process holding the socket); the API writes durable intent (`groups_sync_requested_at`, `wa_groups.leave_requested_at`) and never touches the provider (api.md rule 3).

## Risks / gotchas specific to this phase
- **The blast radius is the whole point.** The blueprint's classifier pauses the instance on 403/402/406. If step 7 is wrong, one group demoting us stops every unrelated DM on that number and needs a human resume. `a_group_forbidden_error_never_pauses_the_instance` and `a_403_on_a_dm_target_still_pauses_the_instance` must both be green — narrowing, not deleting, the restriction path.
- **`shouldIgnoreJid` is a receipt-killer.** If it tests `@g.us`, group broadcast recipients never leave `sent` and `campaign_recipients.delivered_at/read_at` stay null forever. The **receipt scope** of `shouldIgnoreJid` may never test `@g.us`; P21 already enforces this and its test is `a_group_receipt_is_never_filtered_even_when_group_messages_are`. Keep the filter to `status@broadcast` and `@newsletter`; do the group-message decision in the message handler only.
- **Receipt-id collisions are silent.** Without `participant_jid` in `provider_event_id`, 184 group receipts dedupe down to one row and the funnel under-reports permanently. Use an empty string (not `null`) for DMs so the DM hash stays stable and P11's existing dedupe test does not flip.
- **Never store a participant list, in any form** — not a column, not a jsonb blob, not a Redis set, not a log line, not a metric label, not a debug dump in `docs/evidence/`. It is third-party personal data we have no consent for and the raw material for number harvesting (ADR 0017 §2).
- **No add/remove/promote participants, ever, in v1** (safety-compliance skill). Group *creation* is deferred behind tier ≥ 4 + `healthy` and is **not** built this session. Leave is always allowed because it is de-escalation. If a step tempts you toward "just a small add-participants helper", stop — it is a refused feature, not an unbuilt one.
- **The reserve statement is P13's and stays one statement.** Do not add a group counter, a second grantor, or a cap check anywhere else; `check-single-reserve` and test 22 are watching. The group cap is enforced by the two lines that already exist.
- **`recipient_e164` is now nullable.** Anything that assumed non-null — exports, the panel recipient column, metrics, the reaper's repair path, CSV/report code — needs a check this session. A NULL crash on the hot send path is the likely regression.
- **The announce/role check is a courtesy, not a guarantee.** `wa_groups` is at most an hour stale, so a demotion between sync and send is normal and *is* the `group_forbidden` path. Do not turn the pre-send check into a blocking round-trip to the provider.
- **Memory honesty.** A `send_enabled`-groups instance budgets **22 MB optimised / 39 MB pessimistic**; `18 MB` may not be quoted for it (ADR 0018 §2). `DEVICES_PER_PARTICIPANT_ESTIMATE` is DERIVED — label it in the code and do not let it reach a customer-facing number before P26.
- **Copy discipline.** `GROUP_RISK_DISCLOSURE` ships verbatim; group sending is described as *riskier than the same message sent one-to-one*, never as safe, protected or capped-therefore-fine. No "ban-proof" or equivalent anywhere.
- **If the session clock runs out**, the split line is after step 8: `plan/v1/P24a-group-broadcasts-and-metrics.md` carries steps 9-10 (group broadcasts, the metric and the evidence artefact). Add the `P24a` row to `plan/README.md` and write its next-session prompt instead of P25's.
