# P15 — outbox-relay-and-webhooks

**Goal (one line):** every published event leaves the database through one durable `outbox_events` table drained by `ROLE=relay` — coalesced into at most two SSE frames per second per instance, and dispatched to tenant webhook endpoints that are SSRF-guarded at every dispatch, HMAC-signed, and auto-disabled after 20 consecutive failures.
**Status:** done · **Size:** M · **Session:** 1 of 1 (2026-09-02 → 2026-09-03)
**Depends on:** P12, P05 (must be `done`) — transitively P00-P11
**Blocks:** P17 (`notify()` fan-out needs the webhook channel), P19 (low-balance webhook), P23 (`campaign.progress`), P24, P25

**Size warning / declared split line.** This is a full M and the largest single-session risk in Block 4. If the session clock runs out, split at step 6 — **`P15a-outbox-relay-and-webhooks.md`** carries steps 6-10 (safe-fetch, signing, dispatcher, endpoint CRUD, panel) and gets a row in `plan/README.md`; steps 1-5 (outbox, `emit()`, relay, coalesced SSE) stand alone and end green because the SSE hub already has a publisher from P05. Do **not** split the other way: a webhook dispatcher with no outbox would publish from inside business transactions, which ADR 0010 forbids.

## What you are building (3-6 bullets)
- `outbox_events`: one durable, tenant-scoped, ids-only event row written **inside the caller's transaction** via `emit(tx, event)`, plus a guard that makes it the only way to publish.
- `ROLE=relay`: a `SKIP LOCKED` drain loop (500 ms tick, NOTIFY wake + mandatory 1 s poll floor), the coalescer, the backpressure policy, bounded cleanup of published rows, and its metrics.
- Coalesced SSE fan-out: at most **one frame per (client, instance) per tick ⇒ ≤2 frames/s per instance**, newest-wins per `coalesce_key`, batch frame shape, truncation flag — state, not per-message fan-out.
- `platform/http/safe-fetch.ts`: the SSRF guard applied at **every** dispatch — scheme allow-list, our own DNS resolution, RFC1918/loopback/link-local/CGNAT/ULA denial, connect-to-resolved-IP with SNI and `checkServerIdentity` from the original hostname, redirects off, timeouts, 1 MB cap.
- `modules/webhooks`: endpoint CRUD with envelope-encrypted secrets shown once, `X-WP-Signature` signing, the durable `webhook_deliveries` dispatcher with backoff and terminal classes, and 20-consecutive-failure auto-disable with an audit row.
- Panel: batch-frame handling in the SSE client, and a minimal webhook settings screen (list, add, test-send, disabled banner).

## Risks / gotchas specific to this phase
- **`LISTEN` cannot use PgBouncer transaction pooling** (ADR 0010). The relay's NOTIFY listener needs a *direct* Postgres connection, budgeted as one per relay process. If you cannot get one, do not fake it — run the 1 s poll only; correctness does not depend on NOTIFY and the phase still passes.
- **Coalescing must never swallow a terminal state.** Newest-wins is safe only because every coalesced event is a *state hint* the client refetches. If a future event is an audit-relevant fact rather than a hint, it needs `coalesce_key = NULL` and `fanout` without `sse`. The `suppressed_by` column exists so a suppressed row is auditable, not invisible.
- **At-least-once, and say so.** A relay crash between HTTP success and the row update re-delivers. Receivers dedupe on `X-WP-Event-Id`; that sentence goes in `docs/webhooks.md` and in the panel. Never write "exactly once".
- **The SSRF check at configuration time is not a guard.** DNS answers change; the only guard that counts is the one at dispatch, connecting to the IP that was actually checked. This is precisely evolution-api's commented-out check (`webhook.controller.ts:20-23`) — the reference failure this test table exists to prevent.
- **Do not "just make TLS work" against a test server.** `rejectUnauthorized:false` in a fixture that later ships is the classic path to a disabled guard; use a locally generated CA in the test and keep the guard red for everything else.
- **Outbox bloat.** High-churn INSERT/UPDATE/DELETE on one table needs `FILLFACTOR 70`, the partial unpublished index and bounded per-tick deletes; watch `wp_outbox_depth` and dead-tuple growth. Escalation if depth or vacuum becomes the constraint: daily partitions with DETACH, or Redis Streams as the relay transport (ADR 0010's named trigger) — both are decisions, not silent refactors.
- **Metric cardinality (scope delta row 7).** `instance_id` is allowed on at most four gauges fleet-wide and none of them are yours; every metric here is labelled by `fanout`, `topic_class`, `error_class` or nothing.
- **Payload discipline.** The temptation is `{jobPublicId, recipientPhone}` so a tenant's webhook is "useful". Forbidden: ids and enums only (design §6.5, §6.4). `include_message_body` stays `false` with no way to set it in v1.
- **Safety boundary.** A webhook endpoint is a tenant-supplied URL and nothing more. No outbound proxy option, no per-endpoint egress IP selection, no retry path that reaches WhatsApp — the relay never sends a WhatsApp message and never resumes a paused instance.
