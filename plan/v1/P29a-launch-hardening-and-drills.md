## Risks / gotchas (P29 rows that belong to steps 7-10, verbatim)
- **Secret scanning without git is a real trap.** `gitleaks` defaults to a git-history scan and will fail or try to initialise a repo. Use directory/filesystem mode explicitly, assert it in a test, and never run `git` for any reason (ADR 0003). A scanner that errors and returns 0 is worse than no scanner — assert non-zero exit on failure.
- **A scan or a drill that "passes" without running is the failure mode.** Every scanner gets a fixture that must make it fail; every drill writes a timed artefact. The guard meta-assertion applies: a step matching zero files, or a drill with no evidence file, is not a step.
- **The restore drill must never touch production.** Scratch container, scratch port, scratch data directory, and a hard refusal on a production-shaped DSN with a test to prove it. Also verify the **backup encryption passphrase is not the KEK ring passphrase** — two separate compromises is the entire point.
- **Key material discipline during the key drill.** Never print, log, snapshot or paste key bytes, passphrases or the secret storage path. Record locations by description. If the drill fails, the honest outcome is "the key backup does not work and launch is blocked", not a workaround.
- **RTO honesty.** The blueprint's flat 60 min holds at the launch tier only; the scope delta amends it to 4-6 h from backup at 10k with replica promotion as the real path. Write the **measured** number and the tier it was measured at; do not publish an aspirational RTO.
- **Scanner binaries.** `semgrep`, `trivy`, `gitleaks`/`trufflehog` are not in `node_modules`. The CI step must state exactly how each is obtained (pinned version, checksum, no `curl | sh`), and a missing binary must fail the step loudly — the fixture test that proves "fails on a seeded finding" is what distinguishes an installed scanner from a no-op.
