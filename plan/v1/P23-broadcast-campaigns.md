## What you are building (3-6 bullets)
- **Phase A, audience snapshot:** frozen `campaign_recipients` rows (vars resolved at snapshot time, opted-out written `skipped`), one transaction per 1,000 contacts, cursor advanced once per batch, hard ceiling `plan_limits.max_broadcast_recipients` (20,000) enforced at snapshot start as a clear error, never a silent truncation.
- **Phase B, job expansion:** batches of 500 through the **ref-first** CTE (`message_job_refs` insert gates the `message_jobs` insert), per-batch cursor and aggregate counter updates, fleet-wide expansion token bucket, per-client single-expander advisory row, queue-depth backpressure that **holds** in `expanding` instead of erroring.
- **Lifecycle:** `draft → snapshotting → expanding → running ⇄ paused → completed | cancelled | failed`, with cancel enforced by the existing allow-list claim predicate (bookkeeping batches are not the enforcement point) and every resume publishing a wake.
- **The epoch-stranding sweep:** a `session_epoch` bump moves affected `queued` jobs to `blocked_needs_review` with `needs_user_action='session_epoch_advanced'`; re-stamping is a typed human confirmation only, never automatic.
- **Composer, variables and the pre-flight quote:** audience count, skip reasons, client-level "already messaged" deferrals, billable × rate, wallet after, cap-derived ETA labelled an estimate — plus `BROADCAST_DISCLOSURE` enforced by `scripts/check-copy.ts` co-presence.
- **Progress funnel:** `campaign_counters` served from Postgres rollups with `deferred` as a **derived display bucket**, live over the existing SSE `campaign.progress` event.

## Risks / gotchas specific to this phase
- **The ref is inserted first and gates the job. This is not a style choice.** The reverse order (job first, ref `ON CONFLICT DO NOTHING`) produced a sendable job with no `public_id` — unaddressable by the API, invisible in the funnel, and delivered to a real person as a duplicate. `expansion_replay_creates_no_job_without_a_ref` plus the schema assertion are the guards; if either goes red, stop and fix the order, never the test.
- **Cancel is enforced by the claim predicate, not by the bookkeeping batch.** Do not "optimise" the allow-list into a deny-list (`cp.status <> 'paused'`) — that kept a cancelled broadcast sending *and charging* for as long as the stamping batches took. `LEFT JOIN` + allow-list means a missing or unknown status yields zero claims. **`db/queries/claim-jobs.sql` must not be edited in this phase.**
- **Per-row cursor or counter updates will look correct and then melt.** 500 dead tuples per batch on the exact row that drives the progress UI. Aggregate deltas once per batch, `fillfactor` + aggressive autovacuum on `campaigns` and `campaign_counters`.
- **`send_origin='campaign'` is non-exempt.** No cap, window, guard, warm-up tier or frequency limit may be relaxed for broadcast. A broadcast is slower, never faster. Any "priority boost" or "campaign mode" idea that appears mid-session is out of scope and out of bounds.
- **The duplicate-fan-out guard will fire on exactly this shape** (>150 distinct recipients/day with the same content → warn, >500 → `NEEDS_HUMAN_ACK`). Jobs stay **queued** behind a banner until a human acks; that is correct behaviour, not a bug — do not weaken P14's thresholds to make a demo drain.
- **Epoch stranding is silent loss.** Nothing is deleted, so no test catches it by counting rows: the campaign simply stays `running` with zero progress forever. The sweep + `wp_stranded_epoch_jobs > 0` alert is the only detector. Re-stamping is human-confirmed; an auto re-stamp is one refactor away from "keep sending from whatever number is linked now" and is forbidden.
- **`deferred` is a derived display bucket.** Never add it to `broadcast_recipient_status` and never write a row per pacing deny — a deny happens on every claim attempt and would multiply the write rate for a number one indexed count produces.
- **Honest copy.** `BROADCAST_DISCLOSURE` verbatim, always co-present with any surface string containing "Broadcast". The finish time is an **estimate, not a guarantee**. The per-workspace frequency line ships verbatim — it exists so the product never nudges a customer toward hand-rolled number rotation. Never "ban-proof", never "instant bulk sending", never a claim that pacing prevents restrictions. Prices are our pricing, not a provider cost pass-through.
- **No bulk `onWhatsApp()` validation of the audience** (ADR 0017, alternatives): enumerating thousands of numbers is a harvesting pattern we refuse. Invalid recipients surface as terminal `invalid_recipient` failures.
- **`target_kind='groups'` is P24.** Ship the column and the CHECK now; the group snapshot path, `eff_group_daily_cap` and `group_forbidden` land next phase. If a session starts writing group logic here, stop.
- **Do not build the archive/delete cron.** Register the 13-month policy only; P25 owns scheduling. Write anything descoped into this file and carry it into P24's file rather than leaving it in someone's head.
