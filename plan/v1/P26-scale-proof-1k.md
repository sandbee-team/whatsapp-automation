# P26 — scale-proof-1k

**Goal (one line):** the fleet has been run at 1,000 instances under load, chaos and a multi-day drift run on named hardware, and the resulting capacity table — sends/day, statements/send, durable bytes/send, sessions/box, `reserve()` p99, takeover and deploy SLOs, a timed restore RTO — exists with error bars and a measured N, so Gate B can close.
**Status:** todo · **Size:** L · **Session:** 1 of 1
**Depends on:** P25, P10 (must be `done`)
**Blocks:** P27, P29 (launch checklist), and every capacity or price claim (ADR 0016, ADR 0018 §8)

**Size warning — a calendar split is mandatory, not optional.** M6 is a **7-day** drift run
(scope delta / design §6.2: "a 24 h test proves nothing about a 30-day session"). No session can contain
seven days of wall clock. **Split line, fixed in advance:** this session (day 0) does steps 1-9 —
it *launches* the drift run and closes everything else; `plan/v1/P26a-drift-verdict-and-gate-b.md`
(created here in step 9, ~1 hour, run on **day 8**) reads the drift artifacts, writes the leak verdict and
flips the Gate-B banner. **No capacity figure is quotable until P26a is done.** P27 may start after this
session because its levers are architectural and quote nothing. Record both rows in `plan/README.md` at C6.

## Prerequisites (facts, not phases)
- P25 is `done`: every metric in the blueprint's observability table is wired under the four-gauge label allow-list, Prometheus/Grafana/Loki exist in `infra/observability/`, all alerts are defined, and `docs/RUNBOOK.md` exists — **this phase reads those dashboards as its instrument panel; it does not add instrumentation.**
- P10 is `done` (Gate A): `docs/capacity/session-cost.md` exists with its measured per-session bracket and hardware fingerprint, `MAX_SESSIONS_PER_WORKER` is derived from `WORKER_MEASURED_SESSION_MB`, and `scripts/measure/{ramp-sessions,sampler,artifact}.ts` + `app/backend/test/support/mock-wa-peer.ts` + `synthetic-fleet.ts` all exist and work.
- **A Linux measurement target sized for the run**: at the measured blended MB/session, 1,000 sessions needs roughly 20 GB (18 MB) to 40 GB (38 MB) of session RAM *plus* worker baselines, Postgres, PgBouncer and three Redis services. If the available box cannot hold 1,000, see the first gotcha — you run at the largest honest N, you do not extrapolate silently.
- `redis-ctl`, `redis-sig` (`noeviction`), `redis-cache` are separate services; PgBouncer transaction mode is in front of Postgres (scope delta "what breaks first" #8) — measuring `reserve()` p99 on direct connections flatters the number and is not the deployed path.
- A working backup + restore procedure already documented in `docs/RUNBOOK.md` (P25) and a **scratch** Postgres instance to restore into.
- ≥ 3 real linked test numbers still usable from P10 component B (more is better; scope-delta founder open item 6). If zero exist, the real-number component is skipped and the published table says so.
- ADRs 0013, 0015, 0016, 0017, **0018**, 0019 accepted; 0020 (phase/session protocol) in force.

## What you are building (3-6 bullets)
- A **fleet-scale harness**: 1,000 synthetic instances spread across real workers through the real lease/fence/auth-state path, a k6 send-load driver with a realistic multi-tenant mix, and a real-number cohort running beside it.
- The **7-day drift run (M6)** launched with per-hour RSS/heap/GC sampling into replayable artifacts, plus pure, tested drift/leak verdict math in `@wp/domain` that P26a will run over those artifacts.
- The **measured load model (M8/M9)**: statements per send, durable bytes per send, WAL MB/s and sends/day/instance taken from `pg_stat_statements`, `pg_total_relation_size` deltas and the pacing ledger — the three numbers ADR 0018 §7 currently derives.
- The **8-hour 1,000-instance pacing run** with a concurrent 100k-recipient broadcast burst (M14): zero cap violations counted from the ledger, `reserve()` p99 < 25 ms, and no cross-tenant claim-latency damage.
- The **chaos suite as repeatable tests** (M11/M12): `kill -9` of a worker at its cap, `redis-ctl` flush, Postgres outage, rolling deploy under load — each asserting the blueprint's failure-behaviour row, not just "it came back".
- The **timed restore drill at the then-current data size** and the **Gate-B capacity table** with error bars, measured N, run duration and a banner that keeps every figure off tenant-facing surfaces.

## Risks / gotchas specific to this phase
- **If the box cannot hold 1,000 sessions, you run at the largest honest N and the table says N.** Extrapolating 250 → 1,000 and printing "1,000" is exactly the failure Gate B exists to prevent. The honest sentence stays *"the architecture has no known ceiling below 10,000 and has been measured to N"* with the real N (ADR 0018 §8). Raise the box-size gap to the founder as a cost decision, do not paper over it.
- **The 7-day drift run is calendar time.** Launch it in step 3, before the noisy work, and do not compress it to 24 h — the design doc is explicit that a 24 h test proves nothing. If the run dies at day 4, restart it and P26a slides; a 4-day run is reported as 4 days.
- **Never flush `redis-sig`.** It is `noeviction` because losing our end of a ratchet makes already-encrypted inbound messages **permanently unreadable**, and the real-number cohort is attached during this run. The flush drill targets `redis-ctl` only, and the chaos script must refuse any other target.
- **Kill the Postgres *process/container*, never the data volume**, and restore only into a scratch instance. A restore drill that overwrites the running dev database destroys the drift run and the load-model baseline in one command.
- **Self-reported counters are not evidence (invariant 7).** Cap violations come from `pacing_ledger` vs `instance_pacing_state`; job loss comes from row counts; latency comes from the metrics pipeline built in P25 — never from the harness's own tallies.
- **Measure `reserve()` p99 through PgBouncer transaction mode**, at the deployed pool size. Direct connections and a 200-connection pool both produce a flattering number that will not survive production.
- **1,000 sockets exhausts fds and ephemeral ports long before RAM.** Raise `ulimit -n`, widen `ip_local_port_range`, check `net.core.somaxconn`, and record every tuned value in the artifact header — an untuned run fails in a way that looks like an application bug.
- **The measured WAL rate may break the 7-day PITR assumption** in ADR 0018 §7. If it does, write the measured number and raise it; do not quietly re-scope the backup window to fit the result.
- **Real numbers may get restricted during a 7-day run — that is data.** Record it, keep the remaining numbers, continue. No rotation, no failover to another number, no auto-resume: forbidden mechanisms, and a benchmark is not an exception.
- **`needs_reconcile` rows produced by the kill test must each be explained.** A chaos run that "passes" while leaving unexplained unresolved sends is a failed run — the count feeds the human-review workload estimate that P12's SPIKE-2 outcome depends on.
- **Nothing here closes Gate C.** Gate C needs ≥ 2,000 concurrent sessions in production, within SLO, for 7 days. Gate B unblocks capacity claims *at the measured N* only, and only once P26a's drift verdict lands.
