- **Carried from P19's C1 review — three specific debts step 4's `withStaffMutation()` must settle, not just re-state:**
  1. **The audit write is currently NON-transactional for `approve` and `wallet.credit`** (only `reject` is transactional). P19 took the honest-comment option: both file headers now say so plainly and `wp_internal_audit_write_failures_total{route}` counts a lost audit row. `withStaffMutation()` is the real fix — money must not be able to move without its audit row.
  2. **Audit idempotency currently rides on the MONEY layer**, not on the audit table: the row is written only when `creditWalletAndNotify` reports `replayed === false`, because `staff_audit_log` has no unique constraint yet. Step 2's `UNIQUE (idempotency_key)` is what makes this airtight — until then a non-money mutation has no replay authority of its own.
  3. **The approve path's status flip is deliberately IDEMPOTENT, not blocking** (P19 C1 CRITICAL: it used to commit the status in one transaction and the credit in another, so a crash between them stranded a paid top-up forever with every retry rejected at the status gate). `pending` flips and falls through; `approved` falls through with no status write and re-enters the credit, where `wallet_ledger_ext_refs (client_id, 'topup:'||id)` makes it a no-op replay; only `rejected` hard-fails. **Do not "tidy" this back into a `status !== 'pending'` guard** — that reintroduces the money-loss bug. Its regression test is `a_crash_between_the_status_commit_and_the_credit_commit_is_recoverable_by_retry`.

## What you are building (3-6 bullets)
- `/internal/v1` on `app/backend` hardened to production shape: HMAC service token (key ring), `X-Actor: staff:<staff_user_id>`, **mandatory `Idempotency-Key`**, and `withStaffMutation()` — one wrapper that writes the `staff_audit_log` row **in the mutation's own transaction** or the mutation does not happen.
- The v1 internal mutation set: client suspend/reactivate, limit overrides, pricing overrides, wallet credit/adjust/freeze/unfreeze, top-up approve/reject, instance pause/resume, bounded `admin_relax`, campaign cancel, impersonation grant/revoke — each fanning a tenant-visible `notify()`.
- `admin/backend`: staff auth (argon2id + **mandatory** TOTP + IP allow-list + 2-minute access tokens), the `wp_admin_app` pool, and `platformRead(ctx, reason, fn)` as the **only** code allowed to open that pool, with every cross-tenant query registered in `CROSS_TENANT_QUERIES`.
- Time-boxed, audited impersonation: **metadata only by default** (no message bodies), ≤ 30 minutes, revocable, revocation bumps `token_epoch`, and the workspace owner is notified.
- `admin/frontend`: cross-tenant clients/instances/queue/health views, the client detail workbench (suspend, limits, pricing, pacing relax, wallet), the top-up approval queue and the staff audit log viewer — every mutation via `admin/backend` → `/internal/v1`.
- The gate: the role-grant snapshot test proving `wp_admin_app` has **no** INSERT/UPDATE/DELETE on any send-path table, filed as evidence.

## Risks / gotchas specific to this phase
- **`admin/backend` must never gain a write path.** ADR 0014 fact 12: `app/backend` alone owns the send path and DDL. Every mutation is an S2S call to `/internal/v1`. If a session finds it "easier" to write one column directly from the admin pool, that is the exact failure the grant snapshot exists to catch — fix the code, never the snapshot.
- **The audit row is in the transaction or the mutation does not happen.** `withStaffMutation()` is the only entry point; a route that opens its own transaction bypasses it. `a_failed_audit_write_rolls_back_the_mutation` is the guard.
- **"Audit row per read" is scoped honestly.** Triggers do not fire on `SELECT`, so raw `psql` access by a staff member is **not** audited. Either `pgaudit` is enabled for `wp_admin_app` in `infra/` or the claim is not made — write whichever is true into `docs/RUNBOOK.md`, do not write the flattering version.
- **`admin_relax` is the only layer that may loosen, and it is bounded.** Mandatory reason, mandatory `expires_at`, clamped to the platform absolute floor/ceiling, never tenant-settable, and never available as a flag on the tenant API. A client-settable pacing bypass is a forbidden mechanism; so is granting relax *because* an instance was restricted.
- **A staff `resume` is a staff *user*, recorded as such.** Never allow a service token alone to resume an instance out of a restriction pause — that is auto-resume with extra steps.
- **Impersonation reads no message bodies by default**, and the block lives at the route layer, not in the UI. The elevation is a separate grant, separately audited, time-boxed, and the workspace owner is told. If the session feels tempted to "just return the thread so support can see it", stop: that is the safety-compliance boundary.
- **Suspension copy must not imply WhatsApp did anything.** A suspension is our action on our platform: *"Sending is suspended by WP support. Your queued messages are preserved."* No banned claims, no restriction wording, `en` + `hi`.
- **Do not re-create P02/P19 tables.** `staff_users`, `staff_sessions`, `plans`, `plan_limits`, `audit_logs`, `topup_requests` and `staff_audit_log` all exist — this phase `ALTER`s and extends. Re-creating `staff_audit_log` would drop the P19 rows.
- **Metric labels obey the P25 allow-list.** `wp_staff_mutations_total{action}` is fine; a per-client staff gauge is not. No phone, body, name, group subject or wallet `external_ref` in any log line, metric label or audit `metadata` value.
