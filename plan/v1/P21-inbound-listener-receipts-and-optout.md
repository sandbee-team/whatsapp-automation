# P21 — inbound-listener-receipts-and-optout

**Goal (one line):** the inbound half of a connected number is processed headlessly and **stores no message content anywhere** — delivery receipts land in `delivery_events`, a STOP reply writes one `opt_outs` row and cancels that contact's queued jobs, `fromMe` echoes keep feeding P12's reconciler, and a handler that throws writes an `inbound_dead_letters` row instead of losing the event silently.
**Status:** done (2026-09-06; evidence run pending a real number) · **Size:** S · **Session:** 1 of 1
**Depends on:** P20, P12 (must be `done`) — transitively P14 (`opt_outs` + `optout-detect`), P13 (`instance_recipient_contacts`), P11/P03 (`delivery_events` + `delivery_event_ids`)
**Blocks:** P23, P24

> **Scope note (2026-08-26, founder decision — ADR 0021).** The inbox *product* — `chats`, the partitioned `messages` table, message bodies, FTS, media, the conversation thread UI and the reply composer — is **v2 (V2-P3)**. This phase builds the headless listener only. If a step here seems to want a message body, it is out of scope; the mechanical refusal is the test `no_chats_messages_or_media_assets_table_exists_in_v1`.

## What you are building
- One **headless dispatcher** on the session worker's socket handlers: `messages.upsert` / `messages.update` / `message-receipt.update` → filter → admission → `fromMe ? echo-capture : message-signals`. **One try/catch per event**; a throw is one dead letter, never a socket teardown.
- The **receipt handler** → `delivery_events` (`delivered` / `read` / provider-side `failed`) through the existing `delivery_event_ids` dedupe authority, resolving the job via `message_wa_ids (direction='out', wa_msg_id)`. This is the input for the message status timeline, the `delivery_ratio` and `read_ratio` collectors, and (from P23) the campaign funnel.
- **Opt-out keyword detection** on inbound text held **in memory only**, capped at 256 chars, passed to P14's `optout-detect` — which owns `opt_outs`, the mirror, the cancellation (`cancel_reason='opt_out'`, **never** `failed`) and the 30-day confirmation.
- **Contact touch-points only:** `contacts.last_inbound_at` and `instance_recipient_contacts.first_inbound_at = COALESCE(first_inbound_at, now())`. A timestamp is not message content, and P14's link-in-first-message guard reads `first_inbound_at`.
- A per-instance **admission bucket** on `redis-ctl` with a counted, non-storing **shed path**, and `inbound_dead_letters` (ids and hashes only, own transaction) for a handler that throws.
- `packages/domain/src/inbound/ignore-jid.ts`: one scope-typed filter. **Receipts are never filtered by JID.**

**Design refinements recorded here (not silent):**
- `instance_recipient_contacts` is keyed `(client_id, instance_id, recipient_hash)`; a plain UPDATE on a row that does not exist yet (a person who writes to us first) would record nothing and P14's link-in-first-message guard would never learn it → the touch is `INSERT … ON CONFLICT DO UPDATE SET first_inbound_at = COALESCE(instance_recipient_contacts.first_inbound_at, EXCLUDED.first_inbound_at)` (still monotonic, still idempotent).
- `eventTs` in the receipt id is the provider-supplied timestamp when the event carries one (`message-receipt.update`: `readTimestamp`/`receiptTimestamp`), and the empty string when it does not (`messages.update` status changes) — a replayed receipt must hash to the same id, so the wall clock is never an input.
- Receipts are recorded only for `key.fromMe === true` (receipts for OUR sends); `participantJid` is `receipt.userJid` only when `key.remoteJid` ends in `@g.us`, else the empty string (P24 supplies the group value; DMs stay empty).
- Inbound auto-create of a contact (P20-carried note 3) is **NOT built here** — `createContact` requires `createdByUserId`, enforces the plan contact cap (an inbound from a stranger at the cap must not throw), and would resurrect an erased tombstone; each is a product decision, not a listener detail. Existing contacts are touched (`last_inbound_at`); `first_inbound_at` on `instance_recipient_contacts` needs no contact row. Carried to P23 with those three questions.
- Tenant keywords are read per event with one `SELECT keyword FROM tenant_optout_keywords WHERE client_id = $1` inside the same transaction (no loader existed).
- **Receipt identity excludes the provider timestamp (decided at E3, 2026-09-05; ADR filed at C6).** The E3 pass proved that `messages.update` (no timestamp) and `message-receipt.update` (timestamped) both deliver the same logical `delivered`/`read` for one DM; with `eventTs` in the hash they became two `delivery_events` rows and inflated the `COUNT(*)`-based `delivery_ratio`/`read_ratio` numerators. `recordInboundReceipt` therefore hashes `(instance_id, wa_msg_id, event_type, participant_jid)` and passes `''` for `eventTs`; the `@wp/domain` helper keeps the blueprint's five-field form and the parsers still surface `eventTs` for P23's timeline. This narrows blueprint `[R-13s]` for v1 receipts.
- E3 also hardened: per-message field access moved inside the try (a `null` upsert entry is `ignored`, never a rejection); a rejecting dead-letter port cannot reject the dispatcher; `readLimit` values that are not positive integers fall back to the platform default (`wp_inbound_limit_fallback_total`); an empty `chatJid` is not hashed; `protocolMessage.editedMessage` is unwrapped by the extractor (an edited STOP is not missed).

## Risks / gotchas specific to this phase
- **Never store or log message text — at all.** The old inbox rule was "never `rawMessage`"; the v1 rule is stricter: no body reaches any store, log, metric label or dead-letter row. `extractOptOutCandidateText` output lives in one function scope and dies there. The mechanical refusals are `the_inbound_path_writes_no_message_body_to_any_store` and `no_chats_messages_or_media_assets_table_exists_in_v1` — a comment is not a control.
- **A "small" body field will be proposed within two phases** (a panel preview, a dead-letter snippet, a debug dump). The answer is no; it is v2 work and the two tests above exist to make that answer mechanical.
- **The receipt/filter boundary is the one place this fails silently.** If `shouldIgnoreJid` ever drops a group receipt, group broadcasts show permanent non-delivery and the campaign funnel under-reports forever. `a_group_receipt_is_never_filtered_even_when_group_messages_are` and `the_receipt_path_never_consults_the_group_message_filter` hold that line; neither may be weakened.
- **One try/catch per message, and the catch must write.** WhatsApp does not redeliver, so a catch that only logs is permanent loss of a customer's message. The dead-letter write itself can fail — count `error_class='persist_failed'` and keep the socket.
- **Admission control fails open.** Shedding is a fairness control, not a safety control; a Redis outage must not stop opt-out detection.
- **Receipts must not move money.** ADR 0019: the wallet debit fires once at `sent`, keyed on `send_attempts.id`. Wiring `delivered` into billing breaks the guard-keyed single-charge invariant.
- **`redis-sig` stays `noeviction` (ADR 0018 §5).** Inbound still decrypts even though we store nothing; evicting a Signal session makes already-encrypted customer mail permanently unreadable.
- **`reply_rate` has no source in v1 at all** and returns `'unmeasured'` permanently — `'unmeasured'` is never `0`. `delivery_ratio` (scored) and `read_ratio` become measurable at this phase, from `delivery_events`.
- **No git, no CI service, no hooks.** `scripts/ci.ps1` run by a human is the only gate.
