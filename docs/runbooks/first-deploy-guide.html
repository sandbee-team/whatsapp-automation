WP · Deployment

Your first deploy, start to finish

Written for someone who has never opened the AWS console. Every command is given in full, with a line underneath saying what it does. Follow it in order and don't skip section 2.

Time
2–3 hours
Cost
₹0–1,700/mo
You need
AWS account, a domain, a Gmail account

01 What you are building

One server running six processes, all from a single 352 MB image. You do not install Node, or the code, or a database by hand. Docker does it.

ProcessWhat it doesPort
apiThe tenant app and the public API3000
admin-apiYour staff panel: plans, wallets, clients3001
session-workerHolds the WhatsApp connections and actually sends—
cronScheduled cleanup and reconciliation—
relayDelivers events and email—
migrateRuns once per deploy to update the database—

Alongside them run PostgreSQL (the database), two Redis instances, and PgBouncer (a connection pooler). All of that is already written for you in infra/compose/docker-compose.prod.yml.

02 Pick the right server size

Read this before you launch anything. The free tier will not run the full product, and finding that out after setup wastes an afternoon.

AWS gives you 750 hours a month of a t3.micro free for 12 months. That machine has 1 GB of memory. The session worker alone is configured for 3 GB, because it holds live WhatsApp connections in memory. It will not start on a micro.

t3.micro

Free · 1 GB

Everything works except delivery. People can sign up, log in and queue messages. Nothing reaches WhatsApp. Fine for a demo.

t3.small Start here

≈ ₹1,250/mo · 2 GB

The smallest machine that delivers messages. Right for your first real customers.

t3.medium

≈ ₹2,500/mo · 4 GB

Room to breathe. Move here when one server is handling steady traffic.

Do not do this

Do not lower WORKER_HEAP_BUDGET_MB to squeeze onto a free machine. That number decides how many WhatsApp sessions one worker may hold. Lowering it to fit the box removes the protection that stops a worker running out of memory while it is holding live connections.

03 Create the server

Launch the instance

In the AWS console, search EC2 and choose Launch instance.

  • Name — wp-prod
  • Image — Ubuntu Server 24.04 LTS
  • Type — t3.small (see section 2)
  • Key pair — create one, name it wp-prod-key, download the .pem file. This is how you log in. There is no password, and AWS will not give you the file again.
  • Storage — change 8 GB to 30 GB. It is free and 8 GB fills up fast.
  • Region — pick the one nearest your customers and use the same one for everything. For India, ap-south-1 (Mumbai).

Open the right ports

Under Network settings → Edit, remove the default rule and add exactly these two:

TypePortSourceWhy
SSH22My IPSo only you can log in
HTTPS443AnywhereSo customers can reach the site
Never open these

Do not add rules for 5432, 6379, 3000 or 3001. Those are the database, Redis and the two applications. They are reachable only from inside the server by design. Exposing them puts your customer data on the public internet.

Launch it, then click Elastic IP in the left menu, allocate one, and associate it with the instance. Without this the server's address changes on every restart and your domain breaks.

04 Log in and install Docker

chmod 400 wp-prod-key.pem ssh -i wp-prod-key.pem ubuntu@YOUR_ELASTIC_IP

Locks the key file so only you can read it, then logs in. On Windows use Git Bash, not Command Prompt. Replace YOUR_ELASTIC_IP with the address you just allocated.

sudo apt update && sudo apt upgrade -y curl -fsSL https://get.docker.com | sudo sh sudo usermod -aG docker ubuntu exit

Updates the system and installs Docker. The third line lets you run Docker without typing sudo every time. You must log out for that to take effect, which is what exit does.

ssh -i wp-prod-key.pem ubuntu@YOUR_ELASTIC_IP docker --version

Log back in and confirm. You should see a version number. Nothing else gets installed on this machine: no Node, no database, no copy of the code.

sudo mkdir -p /opt/wp /etc/wp/keyring

Creates the two folders the deploy expects. /opt/wp holds the compose file, /etc/wp holds your secrets.

05 Create the S3 bucket for files

This is where images and documents your customers send are stored.

In the console, search S3 → Create bucket. Name it something unique like wp-prod-media-yourcompany, in the same region as your server. Leave "Block all public access" ticked. Under Default encryption choose SSE-S3.

Create a user that can only touch this bucket

Search IAM → Users → Create user, name it wp-prod-s3. Do not give it console access. Attach a policy with exactly these permissions on that one bucket: s3:PutObject, s3:GetObject, s3:DeleteObject, s3:ListBucket.

Then open the user → Security credentials → Create access key → choose "Application running outside AWS". Copy both values now; the secret is shown once.

Create the bucket first

Do not grant s3:CreateBucket. The app tries to create the bucket if it looks missing, and with a correctly limited policy that attempt fails loudly. That is the behaviour you want, as long as the bucket really exists. Create it by hand before first boot and this never comes up.

06 Set up email

Gmail needs an app password, not your normal password. Turn on 2-Step Verification in your Google account, then go to App passwords, create one named wp, and copy the 16 characters.

Know the ceiling

A personal Gmail account sends roughly 500 messages a day. This is used for verification, password reset and alerts, so it is comfortable at 10–15 customers and not at 500. Moving to Amazon SES later changes four settings and no code.

07 Generate your keys

Run these on your own computer, in the project folder.

node scripts/gen-production-key-ring.mjs --out ./key-ring.json

Creates the master key file that encrypts every WhatsApp session and stored secret. It prints a checksum; keep it.

This file cannot be replaced

Lose it and nothing in your database can be decrypted: every customer must re-scan their WhatsApp QR code. It is not a password you can reset. Keep it in three places before you go live — on the server, in an encrypted copy you hold, and in a second sealed copy stored somewhere else. Check all three match with sha256sum key-ring.json.

openssl rand -base64 36 # run this 5 times, one per secret

Generates the five random secrets below. Use a different value for each; never reuse one.

SettingWhat it protects
AUTH_JWT_SECRETCustomer login sessions
ADMIN_JWT_SECRETYour staff login sessions
INTERNAL_API_SERVICE_TOKEN_SECRETService-to-service calls
LEADS_IP_HASH_SECRETContact-form addresses
POSTGRES_PASSWORDThe database itself

08 Write the two settings files

There are two, and mixing them up stops the deploy with a confusing error. This catches people out, so it is worth thirty seconds.

FileRead byCopy from
/opt/wp/.envDocker Compose itself, while reading the configinfra/deploy/compose.env.example
/etc/wp/wp.envThe running applicationsinfra/deploy/wp.env.example

Open each example file, fill in every <placeholder>, and put them on the server at those paths. Then lock them down:

sudo chown root:root /opt/wp/.env /etc/wp/wp.env /etc/wp/keyring/key-ring.json sudo chmod 600 /opt/wp/.env /etc/wp/wp.env /etc/wp/keyring/key-ring.json

Makes the three secret files readable only by the administrator account.

One setting will lock you out until you set it

ADMIN_IP_ALLOWED_CIDRS starts empty, which blocks everyone from the staff panel. That is deliberate. Put your own address in it as 1.2.3.4/32 — search "what is my IP" to find it. Never use 0.0.0.0/0, which lets the whole internet reach your admin panel.

09 Deploy

Two commands, from the project folder on your own computer.

./infra/deploy/build-image.sh

Builds the image, boots it once to check it starts, scans it for known vulnerabilities, and saves it to a file. If the scan finds something serious it stops rather than shipping it.

./infra/deploy/ship-image.sh ubuntu@YOUR_ELASTIC_IP TAG

Copies the image over, loads it, updates the database, and restarts the services. Use the tag the build step printed. The session worker restarts last and only if it was already running, because it is holding live connections.

The very first time, the database is empty, so run the setup by hand on the server:

cd /opt/wp docker compose -f docker-compose.prod.yml --profile tools run --rm migrate docker compose -f docker-compose.prod.yml up -d api admin-api cron relay

Creates the database structure, then starts the four always-on services. The session worker is deliberately left out until you have confirmed everything else works.

docker compose -f docker-compose.prod.yml ps docker compose -f docker-compose.prod.yml logs --tail 50 api

Shows what is running and the last 50 lines from the app. You are looking for api role listening on :3000.

10 Put HTTPS in front

The app listens only on the server's own loopback address. Something has to terminate HTTPS and pass traffic through. Caddy does this and gets certificates automatically.

sudo apt install -y caddy

Installs it.

Point your domain's A record at your Elastic IP, then put this in /etc/caddy/Caddyfile:

app.yourdomain.com { encode zstd gzip reverse_proxy 127.0.0.1:3000 { flush_interval -1 header_up X-Forwarded-For {remote_ip} } }

Gets a certificate, compresses responses, and forwards traffic to the app. flush_interval -1 keeps live status updates working. The header line passes the real visitor address through, which the rate limiter needs.

sudo systemctl reload caddy

Applies it. Then open https://app.yourdomain.com in a browser.

After this works

Set TRUST_PROXY=true and ADMIN_TRUST_PROXY=true in /etc/wp/wp.env, then redeploy. Do this only once Caddy is in front, because those settings tell the app to believe the forwarded address.

11 Check it end to end

Do these in order. Each one proves a different part works.

Only once all seven pass, start the sender and link a real number:

docker compose -f docker-compose.prod.yml up -d session-worker

Starts the process that holds WhatsApp connections. On a 1 GB machine this fails on purpose; see section 2.

A queued message is not a sent message

201 queued means the message is safely stored and will be delivered. It is not confirmation that WhatsApp received it. That is deliberate: the API never sends directly, so nothing is lost if the connection drops mid-send.

12 Before your first paying customer

These are not optional, and none of them is automatic yet.

Known gaps, stated plainly

Backups are documented but not yet wired up, so nothing is backing up until you do it. There is no health check endpoint, so a stuck process will not restart itself or alert you. And the data-retention table published on your legal pages is currently enforced by one job out of eight. Fix the first two before real customers; the third before you make retention promises publicly.

13 When something breaks

A service will not start

docker compose -f /opt/wp/docker-compose.prod.yml logs --tail 100 api

The app refuses to start rather than run half-configured, and the last line usually names the exact setting that is missing.

"required variable POSTGRES_PASSWORD is missing"

The value is in the wrong file. It belongs in /opt/wp/.env, not /etc/wp/wp.env. See section 8.

The staff panel will not load

Your address is not in ADMIN_IP_ALLOWED_CIDRS, or your home connection changed it. Check what your address is now and update the setting.

Everyday commands

# what is running docker compose -f /opt/wp/docker-compose.prod.yml ps # follow the logs live, Ctrl-C to stop docker compose -f /opt/wp/docker-compose.prod.yml logs -f api # restart one service docker compose -f /opt/wp/docker-compose.prod.yml restart api # free up disk after several deploys docker image prune -a

14 Every deploy after this one

./infra/deploy/build-image.sh ./infra/deploy/ship-image.sh ubuntu@YOUR_ELASTIC_IP TAG

That is the whole routine. Two commands from your own machine. The server needs nothing installed on it, and there is no copy of the code there to go stale.
